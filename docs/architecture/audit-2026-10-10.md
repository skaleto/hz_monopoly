# 杭城合伙局架构审计（2026-10-10）

## 结论

项目的领域边界已经存在，但实现仍处于“纵向 Demo 文件”形态：`game-core/index.js`、`server/server.js`、`public/app.js` 各自承担多个职责。当前规模适合开始小步重构，但不适合大爆炸重写。

整体判断：

- 正确基础：服务端权威、纯规则核、SQLite 原子提交、seq/version 单调保护、构建源/生成物分离、完整 E2E 和发布回滚。
- 高风险耦合：运行时 server 依赖 `sims/profiles.js`；客户端复制建设成本与分红公式；路线序列同时存在于 core 和 client。
- 中风险聚合：game-core 同时包含数据、迁移、经济、命令、Bot；server 同时包含认证、HTTP、静态文件、房间、WS、timer、发布 DTO；client 同时包含 API、socket、音频、状态、DOM、动画。
- 暂不处理：测试/文档数量多、旧里程碑文件多。这些不在运行路径，不影响性能或正确性。

## 当前职责与问题

| 模块 | 当前职责 | 评价 | 主要问题 |
| --- | --- | --- | --- |
| `game-core/index.js`（648行） | 棋盘/卡牌/平衡、迁移、状态机、经济、计分、Bot、timeout | 领域内聚但职责过多 | 一个文件有多种变化原因，M1/M2逻辑并存 |
| `server/server.js`（552行） | 配置、认证、HTTP、静态资源、房间、WS、timer、Bot编排、DTO | 低内聚 | 全局单例多，测试受加载时环境影响，且反向依赖 sims |
| `server/store.js`（163行） | SQLite schema、CRUD、事件/快照事务、单调写 | 较好 | 可保留，后续只提取 schema/queries 时再拆 |
| `public/app.js`（242个压缩长行） | API、会话、socket、状态、音频、地图、弹窗、动画、交互 | 低内聚 | 全局状态与DOM耦合，规则公式和路线数据重复 |
| `sims/` | profile、Bot策略、统计 | 本应是外层工具 | 被生产 server 反向依赖，违反分层 |
| `tests/e2e.js`（538行） | 全流程、布局、音效、生命周期、截图/视频 | 覆盖好但过度集中 | 单个场景失败会阻断后续证据，fixture 与断言耦合 |

## 已确认的重复事实源

1. 正式 M2 profile 位于 `sims/profiles.js`，server 直接读取；模拟工具变成生产依赖。
2. 建设成本、下一级分红在 `game-core` 与 `public/app.js` 分别计算。
3. 水线/地铁节点序列在棋盘 `next` 与 `public/app.js` 的硬编码数组同时维护。
4. 卡牌名称/效果在 core 与 client 各有一份。
5. 部分错误码到用户文案只存在于一个超长客户端函数，缺少稳定 view contract。

## 重构优先级

### P0：修正依赖方向（应先做）

目标：不改变任何产品行为。

- 将正式 `CURRENT_RULESET`、M2棋盘、平衡参数、卡牌元数据移入 `game-core/config/`；
- `server` 只依赖 game-core，不再依赖 sims；
- sims 从 game-core 读取正式 profile，再叠加 cautious/target/aggressive 实验参数；
- game-core 对外保持现有 `index.js` facade，避免调用方一次性改动。

### P1：拆分领域核

- `config/board.js`、`config/cards.js`、`config/balance.js`：静态事实；
- `migrations.js`：旧快照归一化；
- `economy.js`：租金、建设成本、板块档位、计分；
- `commands.js`：命令校验与状态迁移；
- `bot.js`：Bot/timeout策略；
- `index.js`：稳定 facade，仅重导出公共接口。

每个迁移提交必须保持 state hash、事件序列和模拟基线一致。

### P2：拆分服务端应用层

- `createApp(deps)` 工厂替代模块加载时创建全局 server/store；
- `auth-service`、`room-service`、`game-service`、`connection-registry`、`decision-scheduler`；
- HTTP 与 WebSocket adapter 只做协议转换；
- 时间、随机数、日志、store 通过 deps 注入。

### P3：客户端模块化

- `src/app/state`：页面/房间展示状态；
- `src/app/api`、`socket`：传输；
- `src/app/render`：纯 DOM view；
- `src/app/effects`：骰子、金币、庆祝、Toast、卡牌；
- `src/app/audio`：音频生命周期；
- esbuild 生成 `public/app.js`，与 dice renderer 一样管理源与产物。

客户端不再计算建设成本/分红；服务端下发可展示的 `upgradeOptions`、板块进度和卡牌元数据。

### P4：拆分 E2E

- smoke/auth/room；
- gameplay/economy/cards；
- lifecycle/reconnect/cancel；
- visual/layout/assets；
- capture-only 截图/视频。

公共 fixture 提供确定的房间/骰子/卡牌状态，禁止依赖前序随机事件。

## 不做的事情

- 不引入微服务、DI框架、Redux、ORM或插件系统；
- 不为了目录整齐重写 store；
- 不把 CommonJS/JavaScript 全量迁移 TypeScript 作为前置；
- 不在重构中顺便改玩法、数值、UI和生产配置；
- 不为重构单独发布线上版本，除非修复明确风险。

## 推荐执行顺序与验收

先完成 P0，再评估是否继续 P1。P0 完成标准：

- server 运行依赖中没有 `sims/`、`tests/`、`scripts/`；
- M1/M2固定种子报告关键指标一致；
- 34/34、完整 E2E、资源可复现全部通过；
- `git diff` 只有文件移动、导入调整与必要测试，不改变事件/HTTP/WS合同。

P1–P4 均应独立分支、独立评审；任一阶段收益不足或回归风险上升即可停止。
